# 03 · 安全与隐私设计

> 这个 App 管的是「钱」和「服务器」。安全不是加分项，是入场券。
> 本文档说明我们保护什么、防谁、以及哪些事我们**刻意不做**。

## 1. 威胁模型

| 威胁 | 影响 | 对策 |
| --- | --- | --- |
| 同步服务器被拖库 | 全量数据泄漏 | 端到端加密：服务器只有密文，且每个密文绑定记录 ID |
| 服务器管理员作恶 | 同上 | 同上；密文无法解密，也无法篡改（AEAD 认证） |
| 设备丢失 / 被他人拿到 | 本地凭据泄漏 | 系统钥匙串（受 OS 锁屏与 Secure Enclave 保护）；App 数据目录不含明文凭据 |
| 中间人攻击 | 窃取令牌或密文 | 生产环境强制 HTTPS；令牌只是随机串，泄漏可单独吊销 |
| 恶意 CSV 文件 | 解析崩溃 / 注入 | 解析器不执行任何内容、不联网；限制行数与大小 |
| 供应链攻击（npm 依赖） | 后门 | 依赖面尽量小（crypto 只用 @noble，服务端只用 fastify） |
| 云厂商 AK/SK 泄漏 | 攻击者控制你的服务器 | 最小权限子账号 + 建议只读；密钥只存本机；签名在 Rust 侧完成，AK 不进 JS |

**不在威胁模型内**：已 root 的设备、被系统级键盘记录器感染的机器、用户主动把口令贴到网上。

## 2. 两个密钥，用途完全不同

| | 本地保险箱密钥（vault key） | 同步密钥（sync key） |
| --- | --- | --- |
| 来源 | 32 字节随机数（`crypto.getRandomValues`） | 用户口令 + 随机 salt，经 scrypt 派生 |
| 存放 | 系统钥匙串 | **只在内存**，不落盘 |
| 用途 | 加密 AK/SK、卡密码等本地凭据 | 端到端加密同步的记录 |
| 换设备 | 不迁移（各自独立） | 口令 + salt 可重建 |
| 丢了怎么办 | 重新录入凭据 | **已同步数据不可恢复** |

两者绝不混用：同步密钥要能跨设备重建，因此强度依赖口令；本地密钥是高熵随机数，
用于保护那些「丢了就麻烦」的凭据。

### 派生参数

```
scrypt(passphrase, salt, N=32768, r=8, p=1, dkLen=32)
```

- `salt` 16 字节，创建仓库时随机生成，**公开**存储在服务端（无 salt 无法跨设备派生）。
- 口令最短 8 位，UI 会给出强度提示（0–4），建议 ≥ 16 位或使用密码管理器生成的短语。
- 参数随记录存进 `StoredKdfConfig`，将来升级参数时老数据仍可解密。

## 3. 加密细节

- 算法：**XChaCha20-Poly1305**（`@noble/ciphers`，纯 JS、审计过的实现）。
- 选它而不是 AES-GCM：24 字节 nonce 可以放心对每条记录随机生成，不存在 96 位 nonce 的碰撞隐患。
- 每条记录一个随机 nonce；`nonce` 与 `ciphertext` 一起存储。
- **AAD = `steward:${collection}:${id}`**：把密文绑定到它所属的记录。
  有人把 A 卡的密文挪到 B 卡的位置，解密会失败——而不是悄悄显示出别人的数据。
- 版本号 `v: 1`：为将来换算法（例如后量子）留迁移路径。

## 4. 凭据存储

| 平台 | 存储位置 | 实现 |
| --- | --- | --- |
| macOS | Keychain | `keyring` crate（apple-native） |
| Windows | Credential Manager | `keyring`（windows-native） |
| Linux | Secret Service（GNOME Keyring / KWallet） | `keyring`（sync-secret-service） |
| iOS | Keychain | 同上（apple-native） |
| Android | Keystore 支持的加密存储 | `keyring` 的 Android 后端 |
| 浏览器预览 | localStorage | **仅开发用**，设置页会显著警告 |

Rust 侧命令：`secret_set` / `secret_get` / `secret_delete`，写入后立即 `zeroize` 内存副本，
单条上限 8KB（防误传大文件）。

云厂商调用（`cloud_list_hosts` / `cloud_power` / `cloud_validate`）全部在 Rust 侧签名并发请求，
**AccessKey 从钥匙串读出后不会回到前端**，也不会进入任何日志或同步请求。

**前端绝不把凭据放进 zustand 的持久化状态**：`syncPassphrase` 在 `partialize` 中被显式排除。

## 5. 服务器能看到什么

| 数据 | 服务器可见 | 说明 |
| --- | --- | --- |
| 卡号、发卡行、额度、余额 | ❌ | 在 `sealed` 里 |
| 商户名、交易金额 | ❌ | 在 `sealed` 里 |
| 云主机 IP、规格、成本 | ❌ | 主机数据本来就不上服务器 |
| 设备名、平台 | ✅ | 配对时提交，用于「我的设备」列表 |
| 集合名（cards / statements） | ✅ | 同步路由需要 |
| 记录 ID、版本号、时间戳 | ✅ | 冲突合并需要 |
| 记录数量、数据大小、同步频率 | ✅ | 元数据侧信道，见下 |

**残留的元数据风险**：管理员能推断「这个用户有 12 张卡、每张卡大约多少笔交易」。
这是所有 E2E 加密同步的固有代价。缓解手段：记录 ID 使用随机 ULID、填充到固定长度（v0.3 可选）。

## 6. 令牌与配对

- 管理员令牌：只在服务端 `.admin.token`（0600）或环境变量里，**不用于日常同步**。
- 配对码：一次性、10 分钟过期、服务端只存 SHA-256 哈希；使用后立即标记 `used_at`。
- 设备令牌：32 字节随机数，前缀 `st_`，服务端只存哈希；泄漏可在服务端删除该设备行来吊销。
- 所有令牌比较走常数时间函数（`timingSafeEqual`），避免时序侧信道。

## 7. 密钥丢失与恢复

| 场景 | 后果 | 建议 |
| --- | --- | --- |
| 忘记同步口令 | 已同步数据无法解密（服务器上只有密文） | 把口令存进密码管理器；或在 v0.3 支持「恢复码」（一次性打印的 256 位种子） |
| 换手机 | 用同一口令 + Vault ID + 新配对码即可 | 配对流程已覆盖 |
| 服务器被删 | 数据丢失 | 定期把 `steward.db` 复制到另一台机器 |
| 设备丢失 | 本机凭据无法被读出（钥匙串 + 锁屏） | 在服务端删除该设备令牌 |

**我们不提供「忘记口令」的找回**——那意味着存在后门。

## 8. 合规边界

- **不碰支付**：不做代扣、代还、转账。因此不需要支付业务许可证，也不接触资金流。
- **不做征信**：不上报、不共享任何用户数据给第三方。
- **个人信息保护法（PIPL）**：自托管模式下，用户是数据控制者，我们不收集任何数据；
  若将来提供托管同步，需要单独做合规评估（数据出境、加密存储、审计日志）。
- **云厂商条款**：用户使用自己的账号与 AK，遵守各厂商的 API 使用协议；建议使用只读子账号。

## 9. 安全 checklist（发版前逐项确认）

- [ ] 生产环境强制 HTTPS，HSTS 开启。
- [ ] 服务端 `.admin.token` 权限 0600，且不在镜像/仓库中。
- [ ] 日志中不出现令牌、口令、密文原文。
- [ ] 依赖审计：`pnpm audit` 无 high/critical。
- [ ] 加密测试覆盖：错密钥、篡改密文、AAD 不匹配都必须失败（已有）。
- [ ] 服务端拒绝畸形记录、超量推送（已有：500 条/次、4MB body）。
- [ ] 移动端截图保护（v0.2：`FLAG_SECURE` / iOS 后台模糊）。
- [ ] 剪贴板不残留卡号（v0.2）。
